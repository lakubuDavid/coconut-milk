# bridge-protocol

## What it is
The canonical RPC envelope for all JS ↔ C++ message passing, defined in
`src/core/messages.h` as `core::JsRPCMessage`. Every bridge message — command
call, return, error, event — uses the same JSON shape.

## Reply model: uniformly async
JS promises are resolved **exclusively** by `__coconut_rpc_receive(id)`.
The `webview_bind` promise value is never used for commands or events —
`webview_return` is not part of the protocol. The JS shim (`bridge.cpp`
injected script) parks a resolver keyed by the call's `id`; C++ replies carry
that same id back through the envelope. This means main-thread (sync-executed)
and worker-executed commands share one reply path.

## Envelope shape

```jsonc
// call:     JS → C++ (request a command; id is generated by the JS shim)
{ "type": "call",   "id": "rpc-3-1730000000", "name": "greet", "payload": { "name": "Ada" } }

// return:   C++ → JS (success) — payload is ALWAYS the full result envelope
{ "type": "return", "id": "rpc-3-1730000000", "payload": { "ok": true,  "data": "Hello, Ada!" } }

// error:    C++ → JS (failure)
{ "type": "error",  "id": "rpc-3-1730000000", "payload": { "ok": false, "error": { "code": "LuaError", "message": "…" } } }

// event:    either direction (fire-and-forget; no id, no reply)
{ "type": "event",  "name": "toast", "payload": { "message": "saved" } }
```

## Key concepts
- **`id`** — generated by the JS shim for calls; echoed verbatim on replies;
  absent for events. It is the promise-correlation key.
- **Reply payload shape is fixed**: `kReturn → {"ok":true,"data":…}` and
  `kError → {"ok":false,"error":{code,message}}`, identical whether the
  command was answered by the Bridge sync executor or a background worker.
- **Routing** (`core::Bridge::onInbound`): `kEvent` → `emitToLua`;
  `kCall` → sync executor when found in `mt_handlers`/main registries,
  otherwise forwarded to the Dispatcher → WorkerPool with `RpcId = msg.id`.

## How it flows
- `WebviewTransport::static_on_rpc` parses inbound `__coconut_rpc` messages and
  hands them to the registered message callback (the core Bridge). With a
  callback registered, the legacy inline handlers are bypassed entirely.
- Replies go out via `transport->send()` as
  `__coconut_rpc_receive('<escaped envelope>')`; events go out as
  `__coconut_dispatch_event(name, payloadJson)`.
- Workers echo `RpcId` from PromiseMessage to Resolve/Reject so the Dispatcher
  can address the right parked promise.

## Gotchas
- **`webview_bind` wraps args in a JSON array**: the inbound callback receives
  `req = JSON.stringify([msgJson])`, so we parse `args[0]` to get the actual envelope
- **Escape sequences**: `common::escapeString(s, '\'')` handles `\`, `'`,
  `\n`, `\r`, `\t` before embedding JSON into `__coconut_rpc_receive('…')`
- **Events are fire-and-forget**: the shim never awaits the binding promise for
  events; an unhandled rejection inside an emit handler surfaces via `_js_log`
- **Legacy**: `src/rpc_envelope.h` (`rpc::Message`) and the inline
  `handleCall`/`handleEvent` path were retired in Phase 3 of the core cutover
