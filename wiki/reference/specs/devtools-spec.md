# DevTools & Vite Integration (Future)

This document covers two related future topics:

1. How the `coconut://` custom URL scheme interacts with the Vite pipeline (dev vs. build behaviour).
2. A proposed architecture for a Coconut DevTools plugin built on top of TanStack DevTools.

Both are deferred to v0.2.0+ and documented here for planning purposes.

---

## 1. `coconut://` scheme — Vite pipeline influence

### 1.1 Architecture reminder

The `coconut://` custom URL scheme is registered at the native webview level via platform-specific APIs:

| Platform | Mechanism | Registered |
|---|---|---|
| macOS | `WKURLSchemeHandler` on `WKWebViewConfiguration` | Before webview creation |
| Linux | `webkit_web_context_register_uri_scheme()` | After webview creation |
| Windows | `CoreWebView2.WebResourceRequested` (stub) | Not yet implemented |

The scheme handler intercepts **every** `coconut://` request made by the webview and:
- Strips the `coconut://` prefix
- Checks if the path matches a registered view name → triggers view navigation
- Otherwise, resolves the path against the app root directory and serves the file
- Serves `Config::fallback_file` on 404 (SPA routing)
- Returns `Access-Control-Allow-Origin: *` on all responses

### 1.2 Build-time influence (Vite + `coconut-vite` plugin)

The `coconut-vite` plugin (`packages/coconut-vite/index.js`) runs during `vite build` and transforms the built `index.html`:

```js
// transformIndexHtml hook — regex replaces relative paths with coconut://
html.replace(/(src|href)=(["'])(\.\.?\/)/gi, (match, attr, quote) =>
  `${attr}=${quote}coconut://dist/`
)
```

**Pipeline stages directly affected:**

| Stage | Influence |
|---|---|
| `base` config | Must be `'./'` so Vite emits relative paths the plugin can rewrite |
| `transformIndexHtml` | Rewrites asset URLs: `./assets/index-xxx.js` → `coconut://dist/assets/index-xxx.js` |
| Asset URL resolution in HTML | The built HTML references `coconut://` scheme URLs exclusively for sub-resources |

**Pipeline stages NOT affected:**

| Stage | Why |
|---|---|
| Rollup bundling / tree-shaking / code-splitting | Happens entirely in Node.js before the transform runs |
| CSS processing (PostCSS, CSS modules, pre-processors) | Pure Vite transforms; no scheme handler involvement |
| TypeScript compilation (esbuild / tsc) | Pure Vite transforms |
| HMR (hot module replacement) | Dev mode uses Vite's HTTP dev server, not `coconut://` |
| Dynamic `import()` resolution | Rollup generates chunks; URLs rewritten in the HTML at build time |
| Source map generation | Generated by Rollup; path rewriting only affects the HTML |

### 1.3 Runtime influence (native scheme handler)

Once the app is built and running inside the Cocount webview:

| Behaviour | How `coconut://` changes it |
|---|---|
| **CORS** | Returns `Access-Control-Allow-Origin: *` — avoids opaque-origin module script errors from `file://` |
| **MIME types** | Resolved by file extension in `routes::mimeForExtension()` instead of the OS or webview defaults |
| **Path resolution** | All paths relative to app root, not the HTML file's directory |
| **404 / SPA fallback** | Unknown paths serve `Config::fallback_file` (e.g. `index.html`) instead of erroring |
| **View navigation** | Registered view names intercepted before file serving → triggers Lua-side view switch |

### 1.4 Friction points

**1.4.1 Dev vs. Production inconsistency**

During `vite dev`, assets are served by Vite's HTTP dev server (usually `localhost:5173`). The `coconut-vite` plugin has an `enforce: 'post'` and only runs during `vite build`, so:

```
vite dev  →  file:// HTML loads, scripts reference relative paths
             (no coconut:// scheme, no CORS headers from handler)
vite build →  HTML references coconut://dist/... URLs
             (scheme handler provides CORS, view routing, SPA fallback)
```

Any feature that depends on scheme handler behaviour (view routing, SPA fallback, custom CORS headers) will behave differently during development. Mitigations:

- Serve a dev-only variant of the scheme handler (e.g. a Vite middleware that responds to `coconut://` paths during dev).
- Or use a conditional transform that rewrites to `coconut://` only in production builds.

**1.4.2 Dual-protocol origin**

The HTML document loads via `file://` (`View.load("dist/index.html")`) while sub-resources load via `coconut://`. This creates a split origin identity:

- `document.location.origin` is `"file://"` (or `"null"` in some webviews)
- `coconut://` responses carry `Access-Control-Allow-Origin: *`
- The webview's injected `coconut.ts` script bridges the gap by exposing the Cocount API globally

This is known to work on all three platforms but is architecturally awkward. A future improvement could serve the HTML itself through the scheme handler (e.g. `coconut://index.html`), unifying the origin.

**1.4.3 Source map resolution in dev mode**

If the built JS source maps contain `coconut://` paths (because the Vite plugin rewrote them), they will not resolve correctly in browser DevTools during `vite dev` where the scheme handler isn't active. At runtime (production) they resolve fine because the native handler serves them.

**1.4.4 Module scripts and CSP**

`<script type="module">` with `coconut://` sources may interact with Content Security Policy. The scheme handler currently does not set CSP headers. If a future version adds CSP support, it must account for the `coconut://` scheme in the policy directives.

## 2. TanStack DevTools-based Coconut DevTools plugin

### 2.1 Overview

[TanStack DevTools](https://tanstack.com/devtools) (alpha, v0.x) is a modular system of packages organised into three layers:

```
Framework Adapters (React / Vue / Solid / Preact)
        ↓
Core Shell + UI Components + EventClient
        ↓
Transport Layer: ClientEventBus ←→ ServerEventBus ←→ Vite Plugin
                  (browser)         (Node.js server)
```

The transport layer is the key piece. It provides:

- **ServerEventBus** (`@tanstack/devtools-event-bus/server`) — runs inside the Vite dev server (Node.js). Creates an HTTP server (or piggybacks on Vite's) that accepts WebSocket and SSE connections, broadcasting events to all connected clients.
- **ClientEventBus** (`@tanstack/devtools-event-bus/client`) — runs in the browser. Listens for `tanstack-dispatch-event` CustomEvents on `window`, re-dispatches them locally, forwards them to the server, and replicates across tabs via `BroadcastChannel`.
- **EventClient** (`@tanstack/devtools-event-client`) — the high-level typed API that plugins use to send and receive events with a `pluginId` and a type map.

### 2.3 Integration points

| Integration point | What it does | Based on |
|---|---|---|
| **Vite plugin entry** | Adds the devtools plugin to the Vite config; must be first | `@tanstack/devtools-vite` |
| **Event bus server** | Runs in Vite dev server, accepts WS/SSE connections | `@tanstack/devtools-event-bus/server` |
| **Event client (JS)** | Instantiated in the webview; captures CustomEvents and forwards to server | `@tanstack/devtools-event-client` |
| **Cocount panels** | Custom Solid.js components inside the core shell | `@tanstack/devtools` (core shell) |
| **Lua → JS event forwarder** | Wraps `coconut.call/emit` to also fire `tanstack-dispatch-event` CustomEvents | Custom (~50 lines JS) |
| **Lua internals exporter** | Emits devtools events from Lua side via the bridge | Custom (~100 lines Lua) |
| **DevTools injection in release builds** | Bundle the panel UI and inject via the scheme handler or `coconut.ts` embed | Custom |

### 2.4 Proposed panels

**2.4.1 View Inspector**
- Tree of all registered views with their type (url/html/file) and current status
- Live preview of which view is active
- Simulate view switching

**2.4.2 Bridge Monitor**
- Real-time log of all RPC messages between JS and Lua
- Filter by message type (call/return/error/event)
- Inspect payloads, correlation IDs, timing
- Highlight slow calls (>100ms)

**2.4.3 Store Viewer**
- Browse the Cocount key-value store
- Search/filter keys
- Edit or delete entries
- Subscribe to store:update events

**2.4.4 Config Editor**
- Live read/write of `coconut.config.lua` fields
- Visual editor for window size, views, keybinds
- Changes apply immediately via `ctx:rebind()` and `ctx:show()`

**2.4.5 Command Log**
- History of `ctx:bind()` registrations
- See which Lua file registered each command
- See call count, last call time, error count per command
- Manually invoke a command with custom params

**2.4.6 Lifecycle Timeline**
- Timeline of view load/mount/unmount events
- Bridge ready/focus/blur/resize/close events
- Hot-reload triggers

### 2.5 Data flow

```
JS app code throws / logs / calls coconut API
  │
  ├─ uncaught exception → window.onerror → bridge → debug::error  (Layer B ✓)
  ├─ console.log/warn/error → platform console handler → bridge  (Layer C — planned)
  ├─ coconut.call/emit → bridge → Lua handler response
  └─ devtools CustomEvent → ClientEventBus → WS → ServerEventBus
       └─→ broadcast to all connected clients (other tabs, server-side listeners)
       └─→ received by DevTools panels in the core shell
```

### 2.8 Caveats and risks

- **TanStack DevTools is alpha** (v0.x.x). APIs may break between releases. Lock to a specific version.
- **The core shell is built with Solid.js**. Custom panels need Solid knowledge. If that's a barrier, a standalone UI can be built using the EventClient directly without the core shell.
- **Only active during `vite dev`**. The event bus server lives in the Vite dev server process. For release builds, a standalone event bus server or direct Cocount bridge routing would be needed.
- **Performance overhead**. The event bus adds a CustomEvent dispatch per Cocount bridge call. Should be negligible but worth measuring.

### 2.9 Alternatives considered

**2.9.1 Standalone Cocount DevTools (no TanStack)**
Build everything from scratch: a Vite plugin that injects a custom DevTools UI, a WebSocket server for live data, and a panel UI in the webview. More control, much more work.

**2.9.2 Chrome DevTools Protocol (CDP)**
Use the `--remote-debugging-port` flag to connect Chrome DevTools to the webview. Gives full JS debugging (sources, console, network) without any Cocount-specific integration. However, it provides no Cocount-specific insights (view tree, bridge traffic, Lua state).

**2.9.3 Electron devtools-extensions**
WebExtensions API is not available in the embedded webview on any platform. Not feasible.

**2.9.4 Custom Vite WebSocket plugin**
A minimal custom WebSocket server in the Vite plugin that forwards Cocount bridge events to a simple HTML panel. Lighter than TanStack but lacks the panel system, cross-tab sync, and typed event client.

### 2.10 Recommended approach

Adopt **TanStack DevTools transport layer** (event bus + event client) for the communication infrastructure. Build custom Cocount panels for the specific debugging needs. This gives:

- Proven real-time event transport (WS/SSE/BroadcastChannel)
- Structured typed events
- Cross-tab sync for free
- Plugin architecture for Cocount panels
- Integration with Vite dev server

The alternative of building everything from scratch would require re-inventing the same event bus infrastructure.

### 2.11 Future possibilities

- **Lua REPL in DevTools**: Evaluate arbitrary Lua expressions from a panel and see results in real-time
- **Performance recording**: Capture dispatch queue timing, render cycles, bridge latency
- **Network inspection**: View all `coconut://` requests with timing, size, and MIME type
- **State snapshots**: Capture and restore app state (store, view stack, command handlers)
- **Mobile preview**: Simulate different window sizes from a panel
